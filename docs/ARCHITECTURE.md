## 需求变更历史

- **2026-08-14 初版**：接剪映，用剪映的云端功能（识别字幕/换音色/人声分离/音乐库）

## 一句话目标

把分镜文件夹里的片段按「钩子 + N 个卖点 + 结尾促单」组合成多条竖版短视频，
带字幕、统一配音音色、BGM，导出到桌面 `VEDIO抖音`（不存在则自动创建）。

不必用音色转换（VC）去保留原时长。**待用户确认画面里有没有真人正脸说话。**

### 剪映自带 ffmpeg 的能力边界【实测】

`D:\Tool\JianyingPro\11.2.0.14339\ffmpeg.exe`

- ✅ 滤镜：`overlay` `scale` `concat` `amix`
- ✅ 编码器：`h264_nvenc` / `h264_amf` / `h264_qsv` / `h264_mf`
  → 覆盖 N卡/AMD/Intel/MediaFoundation，**任何 Windows 机器都能硬编码**
- ❌ **没有** `drawtext` `subtitles` `ass` → **烧不了字幕**
- ❌ 没有 `libx264`，且 `--disable-ffprobe`（探测时长用 `ffmpeg -i` 解析 stderr）

**结论**：要烧字幕就得自带完整 ffmpeg 构建，或走 Pillow 渲 PNG + `overlay` 叠加。
已验证 Pillow 能加载新青年体（内部名 `WenYue XinQingNianTi (Non-Commercial Use)`）。

### 换完整 ffmpeg 构建后，上面的约束已解除【2026-08-15 实测】

打包 exe 要脱离剪映，所以改用完整构建，**已随包入库**为项目根 `ffmpeg.exe`
（不进版本库，见 `.gitignore`）。来源 BtbN GPL build
`ffmpeg-n8.1-latest-win64-gpl-8.1.zip`，实测版本 `n8.1.2-44-g7c533d0f86`。

| 项 | 剪映自带 | 完整构建 |
|---|---|---|
| 体积 | 0.5MB | **144.4MB** |
| 链接方式 | **动态**，依赖同目录 `avcodec-61.dll` 等 7 个 `av*`/`sw*` DLL | **静态，零 DLL 依赖** |
| 能否单独分发 | ❌ 只拷 exe 得到废文件 | ✅ 单文件即可 |
| `drawtext` | ❌ | ✅ 实跑编码通过 |
| `libx264` | ❌ | ✅ 实跑编码通过 |
| `ffprobe` | ❌ `--disable-ffprobe` | ✅ 独立 `ffprobe.exe` |

⚠️ **别照抄旧版记录的 87.5MB**。那是 2026-02 另一份构建（已从本机消失）。
换构建后体积翻倍，直接把分发包从预估的 200-250MB 推到 **427M**。
换 ffmpeg 来源前先量体积。

**但字幕方案仍保持 Pillow 渲 PNG + overlay**，不改用 `drawtext`：
现方案已端到端验证，`subtitle.py` 处理好了中文折行与孤立标点合并，
换过去要重做转义和字体加载，无收益。（见 `CLAUDE.md` 铁律 3。）

**`libx264` 的真实价值是软编码兜底**：`render.py` 原先只试四个硬编码器、全不可用就报错，
无独显的办公机会当场跑不了。现已加在 `ENCODER_CANDIDATES` 末位。
实测强制用它出片：29.0MB / 3.7s，ffprobe 确认 h264 720x1280 24fps 919 帧
38.29s + aac 双声道 —— **软编码路径已验证，不是只加了配置**。

### GPL 义务：不止 ffmpeg.exe【2026-08-16 实测】

许可文件、源码承诺、依赖清单都在 **`licenses/`**（进版本库）。
索引 `licenses/README.md`，浏览器版 `licenses/index.html`，界面页脚有入口。

随包 `ffmpeg.exe` 的 `ffmpeg -L` 自报 **GPL version 3 or later**，
configure 带 `--enable-gpl --enable-version3 --enable-libx264 --enable-libx265`。

**⚠ `av.libs/` 里还有两个 GPL DLL，随 PyAV 18.1.0 的 wheel 来的，我们从没要过**：

```
libx264-165-*.dll   2.2MB      libx265-*.dll
```

性质与 `ffmpeg.exe` **不同**：后者是 `subprocess.run()` 起的独立进程
（`render.py:27`、`asr.py:67`），隔着进程边界；这两个是**加载进 Ave 自己进程**的
（`faster_whisper/audio.py:15` 的 `import av`）。

**删除试验做了，结论：删不掉。** 解析 `avcodec` 的 PE 导入表 ——
这两个在 **load-time import（`.idata`）**里，19 个导入项就有它们，不是 delay-load。
移走后 `avcodec` 直接 `Could not find module ... or one of its dependencies`，
PyAV 起不来 → 语音识别整条链废掉；放回去立刻恢复（对照实验）。
`Ave.spec` 里写了注释防后人再试。

`avcodec_license()` 自报 `LGPL version 3 or later`，但 configure 带
`--enable-libx264/x265`，而这俩在 FFmpeg `configure` 的
`EXTERNAL_LIBRARY_GPL_LIST`（第 1997-1998 行）里。自报值与实际链接内容不一致，
**按 x264/x265 的 GPLv2 走是安全假设**。要彻底移除只剩自编 PyAV 一条路，成本远高于收益。

**⚠ 源码承诺不能引用 BtbN 的 `latest` tag** —— 它是滚动的。实测 release
`published_at` 2026-08-15T13:26:38Z，同名资产
`ffmpeg-n8.1-latest-win64-gpl-8.1.zip` 的 `updated_at` 同刻被**原地重新上传**。
过段时间下回来就不是包里这份了，等于没给源码。改用钉死的
`autobuild-2026-08-15-13-02` + `ffmpeg-n8.1.2-44-g7c533d0f86-win64-gpl-8.1.zip`
（文件名自带精确版本）。上游 commit `7c533d0f86f13a06ec93968f6194349665b3536a`
已核实存在（2026-08-14T23:17:34Z）。
`准备素材.py` 里的 `FFMPEG_URL` 与 `SOURCE-OFFER.md` 是同一个 release，
`--check` 校验两处没漂。

🔴 **`SOURCE-OFFER.md` 里仍有 `<待填>`（源码归档 URL）—— 对外分发前必须补。**
写文档不等于履行义务，得真有个能下载到东西的地方。

### 打包相关实测数据【2026-08-15 实际打包后修正】

| 项 | 值 |
|---|---|
| PyInstaller | 6.19.0 |
| ctranslate2 | `collect_all` 拿到 3 个 DLL，其中 `ctranslate2.dll` **59.3MB**（打包后 57M）。**首次构建即成功，没要改 spec** |
| faster_whisper 资产 | `assets/silero_vad_v6.onnx` **1.2MB**（不是 18MB），**必须打进包**，否则幻觉闸门失效 |
| **分发包实测** | **427M**（不含 1.5G 模型）。排 torch 前是 **4.5G** |
| 分发形态 | **onedir 不用 onefile** —— onefile 每次启动要解压到 temp，慢且原生 DLL 易出问题 |

**① 必须排掉 torch，否则包体 4.5G**。torch 一个人占 4.2G，纯粹被传递依赖拖进来 ——
faster-whisper 是 ctranslate2 的重实现，推理走 ctranslate2、VAD 走 onnxruntime，
**运行时根本不碰 torch**。`Ave.spec` 的 `excludes` 排掉 torch/torchvision/torchaudio
后 4.5G → 289M（加真 ffmpeg 后 427M），且实跑 exe 确认服务与识别都正常。

**② PyInstaller 6 的 onedir 把 datas 放进 `_internal/`，不是 exe 同目录**。
即 `sys._MEIPASS`。`config._app_root()` 返回的是 `dirname(sys.executable)`，
只用它会导致**冻结后 ffmpeg / 字体 / 前端全找不到**【实测】。
故 `config.py` 加 `_bundle_root()` + `_resource()`，按
「exe 同目录（人手动拷的优先）→ `_internal/`（打包进去的）」两处都找。

**③ 起子进程一律走 `sys.executable`**。`server.py:pick_dir()` 原先硬编码
`subprocess.run(["python","-c",code])`，办公机不装 Python 必然失败；
且**冻结后的 exe 不接受 `-c`** —— 要跑的代码必须是 exe 的真实子命令。
故新建 `ave/launcher.py` 提供 `--pick-dir`，冻结态调 exe 加该参数、源码态调
`-m ave.launcher`。（见 `CLAUDE.md` 铁律 10。）

### 应用目录 / 用户数据目录分离【2026-08-15】

```
D:\Ave\                    应用目录，更新时整体替换
  Ave.exe  _internal\（含 ffmpeg.exe / fonts\ / web\）
%LOCALAPPDATA%\Ave\        用户数据，更新不碰
  models\fw_medium\  cache\asr.json  bgm\  .work\
```

模型/缓存/BGM 用 `config._first_existing([用户目录, 应用目录], 用户目录)`
**查找顺序**，不是写死用户目录 —— 后者会让源码态丢掉已有的 1.5G 模型和
55 条 ASR 缓存（重下、重识别），且**卖点语义聚类会因读不到 ASR 原文而
全部回落用标签、去重质量静默变差**。

`WORK_DIR` 例外，固定在用户数据目录：冻结态应用目录可能不可写
（如装在 Program Files），且那是跑完就删的临时文件。

### ⚠ 首次运行时语义聚类会退化【2026-08-15 实测】

`pipeline.build_theme_map()` 在 `run()` 开头调用，**早于任何语音识别**。
全新安装的 exe 用户目录里没有 ASR 缓存，`point_texts()` 于是 33 组全部
回落用文件名标签 —— 标签聚出 14 簇、ASR 原文聚出 10 簇，去重强度不同，
**首批成品的去重质量弱一档**。

跑完这一遍缓存就写进用户数据目录（实测 55 条），第二次起就用 ASR 原文。
这也解释了 exe 首次全量跑 443s 而源码态只要 145s —— exe 把 55 个片段全重识别了。

要彻底解决得把聚类挪到识别之后，或首次运行先批量识别再组合。当前未改。

### 播放接口：Starlette 原生支持 Range【2026-08-15 读源码确认】

`FileResponse` 会解析 `Range` 头、返回 `206` 和 `Content-Range`（`starlette/responses.py`
有 `_parse_range_header` / `_handle_single_range`），所以 `<video>` 拖进度条能直接 seek，
**不用自己切分片**。实测 `Content-Range: bytes 0-1023/26906059`。

安全边界：服务只听 127.0.0.1，但**浏览器里任何网页都能往本机端口发请求**，
所以 `_safe_output_file()` 用 `basename` + `realpath` 把路径限死在输出目录内、只放 `.mp4`。

## 命名规范（用户 2026-08-14 确认）

```
钩子-内容概括-N
卖点M-内容概括-N
结尾促单-内容概括-N
```

- `M` = 顺序（卖点1 是脚本里第一个展示的内容）
- `N` = 变体号（同一内容可能生成多个）
- `内容概括` = 这个分镜讲的卖点是什么（沥水/收纳/颜值……）

**现存素材有不合规的**，解析要容错【实测】：
- `1/钩子-1.mp4`、`1/钩子-2.mp4` —— 无内容概括
- `6/卖点-滴水承接-1.mp4` —— 卖点无 M 序号
- `3/卖点0-...` —— 从 0 开始编号

## 组合规则

- 跨文件夹混池：1~7 的钩子/卖点/结尾各自汇总成三个池
- 每条 = 1 钩子 + N 个卖点（默认 5，可配）+ 1 结尾
- **每个钩子用满 3 次即换下一个**（要计数器）
- 片段内顺序：钩子 → 卖点（按 M 升序？待确认）→ 结尾
- **同卖点避免混在一块** —— 待确认判定依据是 M 序号还是内容概括

## 字幕样式需求

- 字体：新青年体（**授权有问题，见下**）
- 字号：10-15（剪映 UI 刻度，映射到 720x1280 画布的像素值待定）
- 位置：正中央偏下
- 阴影：开，纯黑

## 音频需求（有内部矛盾，待澄清）

- 需求 4：所有分镜配音统一为「小姐姐」
- 需求 6/7：仅保留人声，背景声全部去掉

脱离剪映后，最自然的解释是：**ASR 识别口播 → TTS 用「小姐姐」重新生成 →
丢弃原音频**。这样需求 6/7 自动满足（原背景音随原音频一起丢掉），

## 已废弃的调研结论（仅作历史记录，当前方案不用）

之前为「接剪映」方案做的调研，现已不适用但避免重复踩坑：

- 剪映 11.2 主窗口是 Qt 6.2 `MainWindow_QMLTYPE_556`，**UI 树 children: 0**，
  整窗口一个不透明矩形，零子控件【实测】。安装目录无 Qt accessibility 插件。
  → 任何基于 accessibility 的界面自动化在 11.x 上不可行
- 剪映无命令行接口；11.x 无原生批量导出
- `draft_content.json` 加密；能解密的公开工具只验证到 10.6.5
- 剪映向下兼容明文草稿，脚本写明文 JSON 它能打开
- 「小姐姐」不在剪映 57 个**变声**预设里（导出全表确认），
  它是**口播换音色/文本朗读**的 TTS 音色

## 卖点语义重复：已处理【2026-08-15】

跨文件夹混池会把不同脚本版本讲同一件事的卖点混进一条视频，例如
`4/卖点3-错层拿取反复证明` 与 `2/卖点3-错层不挡手` 与 `1/卖点3-错层拿取，不互相遮挡`。
用户 2026-08-14 曾指示先不管，**2026-08-15 改为必须处理**（实测 21/39 条中招）。

**做法**：`combo.py:auto_cluster()` 从 ASR 原文自动聚类 —— 汉字二字组 +
文档频率自动停用词（超 34% 文档出现的自动丢）+ Dice 相似度 + 平均连接层次聚类。
抽样时同簇不重复入选，并用 Madow 系统抽样让入选概率 ∝ 簇成员数。
界面开关「卖点自动分类去重」默认开，CLI 对应 `--no-dedup`。

**⚠ 曾走过的弯路，别重走**：

1. **手工映射表方案已被否**。第一版硬编码 33 条卖点的主题表，实测重复 27→0
   很漂亮，但只对建表那个产品有效 —— 换文件夹后所有组落进「自成一类」兜底分支，
   不报错、静默退化成完全不去重。而且那个 0/39 是**循环论证**：手工表本身就是
   判重的尺子，按自己的尺子量当然是 0。（见 `CLAUDE.md` 铁律 9。）
2. **按成员数逐次加权抽取是错的**。顺序抽取时权重会随抽走的簇重新归一，
   得到的入选概率**不与权重成正比** —— 实测单成员簇仍有 11 次曝光，期望只有 5.9。
   必须直接把入选概率定成 ∝ 成员数（超 1 截顶）+ Madow 系统抽样。
   （见 `CLAUDE.md` 铁律 10、`combo.py:inclusion_probs()`。）
3. **按标签而非 ASR 原文分类会弱一档**。标签是人写的概括、可能有偏差；
   原文才是观众听到的内容。例 `4/主卖点机制纠正` 原文「两层杆把抹布错开挂，
   湿物自然分开」落点是干燥而非易用性。

**实际效果（20 seed 平均，判重基准用人工分的 9 类）**：

| | 同主题重复 | 含三连的条数 |
|---|---|---|
| 关闭去重 | 30.8/39 | 4.8 |
| 阈值 0.10（紧，已弃用） | 18.1/39 | 0.9 |
| **阈值 0.05（松，当前）** | **13.8/39** | **0.2** |

**注意阈值越低越容易合并**（低 = 松 = 去重更狠），别把 0.10 当成「松」。

**仍是缓解不是消除**：剩余成对重复源于汉字二字组搭不了近义词的桥 ——
「滴下来的水由底盘接住」和「底盘把滴水留在架子这一块」是同一个意思但用词不同。
要再往下压只剩引入词向量一条路（多模型依赖，违背零依赖原则），当前接受现状。

### 实测的坑（别再踩）

- **`apad=whole_dur` 在剪映裁剪版 ffmpeg 上不按语义工作**（要 5s 只给 2.88s）。
  改用显式 concat 一段静音
- **`atempo` 只接受 0.5~100**，超出静默失败。且配音比画面短时应补静音而非慢放，
  慢放念稿会明显拖腔
- **Whisper 领域词必须喂 `initial_prompt`**。不喂时实测错误：
  抹布→师妈不、湿物→失误、镂空篮→楼空栏、悬空→玄空、洗碗布→石马布、高低杆→高低干。
  喂词表后全部修正
- **small 模型不够用**，专业词错得多；medium 明显更准（1.5G vs 484M，
  单片段 CPU 4s vs 1.6s）
- **白字必须描边**。厨房台面是浅色，纯白字+弱阴影会发虚
- **孤立标点会单独成行**（句末「。」掉到第二行），折行后要合并回上一行
- **`Windows GBK` 编不了 `⚠ ✓ ✗`**。CLI print 这些字符、输出重定向到文件时
  直接 `UnicodeEncodeError` 崩，全量跑不完。入口处 reconfigure stdout/stderr 为 UTF-8
  + `errors='replace'` 兜底【2026-08-15 踩过】
- **不传 seed 的组合预览无法和已渲成品对应**，且会**伪装成正确的**。
  `build_combos` 按 `hook_groups` 顺序遍历、每组用满 `hook_limit` 次，顺序是确定的；
  多数钩子组只有一个变体，`rng.choice` 每次返回同一片段 —— 所以**钩子永远看着对，
  只有卖点和结尾在漂**。实测同一请求 5 次出 4 个不同结尾。
  要把成品和组合对应上，必须在渲染时落 manifest，不能靠序号事后join【2026-08-15 踩过】
- **stdout 重定向到文件是块缓冲**，进度日志不会实时出现（`wc -c` 长时间为 0）。
  想看进度改数输出文件数，或加 `flush=True`

## 钩子归组规则（2026-08-14 已确认并改代码）

用户确认 `1/钩子-1.mp4`(7.08s) 与 `1/钩子-2.mp4`(5.06s) 是**两个不同的钩子**，
不是同一钩子的两个变体。

归错组会少产出视频，不归组最多是同一条里出现两个相似片段。

结果：钩子 13 组 → **产出 39 条**。真变体仍正确归组
